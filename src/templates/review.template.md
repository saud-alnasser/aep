# Template — the review rule

Copy to `.aep/rules/review.md`. It is optional and the repository's own.
`[[skills/review]]` loads it first, where it exists, before the other rules.

**Keep it under 30 lines.** Every review reads it, so each line costs a little
on every review. Say what a reviewer cannot learn from the code; leave out what
a linter, formatter, or type-checker already enforces.

```markdown
---
use-when: "reviewing a diff in this repository"
---

# Rule — review

## What failure looks like here

| Area | It fails when |
| --- | --- |
| `docs/` | it lies: it describes behaviour the code no longer has |
| `config/` | it misroutes: a value sends traffic or data to the wrong place |
| `<area>` | <the failure that matters in this area> |

## Skip

- `<path>`: generated by `<command>`; review the source instead.
- `<path>`: <why it is not worth a reviewer's budget>.

## Also

<Anything else a reviewer here must know, one line each.>
```

**Name the failure, not the virtue.** "Docs must be accurate" tells a reviewer
nothing it did not assume. "Docs fail when they describe behaviour the code no
longer has" tells it what to check.
